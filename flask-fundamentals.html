How a Flask request works

Every vulnerability in this lab happens somewhere in the path a request takes through your app. Here's that path in Flask — one small route, traced stage by stage — showing what the framework secures for you and what it leaves to you. The danger is almost always at the boundary where untrusted input arrives.

A minimal Flask route
from flask import Flask, request, render_template, session, abort app = Flask(__name__) @app.route("/profile") # 1 routing def profile(): name = request.args.get("name") # 2 input enters — trust boundary if "user_id" not in session: # 3 authn / authz abort(401) row = db.execute( # 4 data access "SELECT * FROM users WHERE name = ?", (name,)) return render_template( # 5 rendering (Jinja2) "profile.html", user=row) # 6 response + session cookie

Green stages are handled by Flask; amber stages are yours to secure.

1

Routing

Flask handles

@app.route("/profile") maps the URL to your view function. Werkzeug (Flask's engine) parses the raw HTTP request into a tidy request object.

SecurityEvery route you expose is attack surface. Keep internal or admin routes off public URLs and behind checks.

2

Input enters

Your job

request.args, request.form, request.json, request.cookies — all of it comes from the client, so all of it is attacker-controlled.

⚠ Trust boundary

SecurityValidate and normalise everything here. This is the source for SQL injection, XSS and path traversal.

3

Authentication & authorisation

Your job

Flask gives you session — a signed cookie — but who the user is and what they may do is logic you write. The abort(401) here is a check you added.

SecurityMind the difference: AuthN vs AuthZ. See it break in Broken Authentication.

4

Data access

Your job

The ? placeholder with (name,) is a parameterised query — the database treats name as a value, never as SQL. Flask does nothing here; the safety is your choice of query style.

SecurityBuild strings by hand instead and you get SQL injection. Parameterise, or use an ORM like SQLAlchemy.

5

Rendering the template

Flask handles

render_template runs Jinja2, which auto-escapes variables by default — so {{ user.name }} can't inject HTML. This is free XSS protection you get just by using templates.

SecurityYou lose it the moment you use | safe, render_template_string or build HTML by hand on user input. See XSS.

6

Response & session cookie

Shared

Flask signs the session cookie with SECRET_KEY (tamper-proofing, not encryption). You set the cookie flags — HttpOnly, Secure, SameSite — and, importantly, Flask does not protect forms against CSRF by default.

SecurityKeep SECRET_KEY out of the code (→ secrets & config), harden the cookie (→ session security), and add CSRF tokens with Flask-WTF. See CSRF.

Four of the six stages are yours to secure — the framework is a strong default, not a guarantee. The lessons linked above each take one of these stages apart.
